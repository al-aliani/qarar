# تصميم تجميد نتائج الدراسة (Result-Freeze) — وثيقة تصميم فقط، بلا تنفيذ

**الحالة:** تصميم مبدئي — قرار المالك: "قريباً، جهّز التصميم فقط" (2026-08-28). التنفيذ الفعلي
مؤجَّل حتى أول عميل دافع حقيقي.
**السلف:** المرحلة 2 من خطة إعادة تقييم الطبقات الـ16 (`C:\Users\WinDows\.claude\plans\tender-floating-thompson.md`)
— بانر إصدار المحرك (`ENGINE_VERSION`، `_meta.engineVersion`) هو الأساس الذي تُبنى عليه هذه الميزة.

---

## 1) المشكلة التي لا يحلّها بانر إصدار المحرك

بانر إصدار المحرك (المرحلة 2) حلّ جزئي متعمَّد: **تنبيه فقط، لا تجميد فعلي**. كل عرض وكل تصدير
يعيد حساب `calculateStudy` حياً بالمحرك الحالي دائماً — لا يوجد أي لحظة يمكن للعميل أو صاحب
الدراسة أن يقول فيها بثقة: "هذا الرقم بالضبط (NPV/IRR/القرار) هو ما دفعتُ مقابله / ما أرسلته
للبنك يوم كذا". لو تغيّر `ENGINE_VERSION`، أو تغيّرت مدخلات الدراسة لاحقاً (تعديل عرضي)، فإن كل
الأرقام المعروضة تتغيّر معها بصمت — البانر يُنبّه أن شيئاً تغيّر، لكنه لا يحفظ **ما كان عليه** قبل
التغيّر.

هذا مهم تحديداً لأن المنتج يبيع "قراراً" (GO/NO-GO) بمبلغ مالي حقيقي — العميل يدفع مقابل تحليل
في لحظة معيّنة، ويستحق نسخة رسمية ثابتة من تلك اللحظة، لا رقماً يتغيّر تحته.

## 2) شكل السجلّ الثابت (Snapshot Shape)

السجلّ الثابت يجب أن يحوي **كل** ما يلزم لإعادة إنتاج القرار المعروض للعميل وقتها، لا المدخلات
فقط:

| الحقل | المصدر | لماذا |
|---|---|---|
| `inputs` (jsonb) | نسخة كاملة من `study.data` وقت الالتقاط | لا قيمة لمخرجات بلا مدخلاتها — أي تدقيق لاحق يحتاج التكرار |
| `outputs` (jsonb) | نتيجة `calculateStudy(inputs)` وقت الالتقاط بالضبط | **هذا هو الغائب اليوم في `study_versions`** — الجدول القائم يخزّن المدخلات فقط (عمود `data`)، لا نتائج المحرك |
| `engine_version` | `ENGINE_VERSION` من `engine.js` وقت الالتقاط | يفسّر أي فرق لاحق عن الحيّ |
| `schema_version` | `study.version` (schema.js) وقت الالتقاط | توثيقي بحت — لا علاقة له بالحساب (نفس التمييز الذي أرسته المرحلة 2 بين الرقمين) |
| `capture_trigger` | enum: `payment` \| `manual_export` \| `owner_request` | يوثّق **لماذا** جُمّد هذا السجلّ تحديداً |
| `order_id` | `orders.id` (لو الزناد دفعة فعلية) | يربط السجلّ الثابت بإثبات الدفع نفسه — أقوى رابط قانوني ممكن |
| `created_by` | `auth.uid()` | من طلب الالتقاط (المالك عادة، النظام في حالة `payment`) |
| `created_at` | `now()` عند الإدراج | ثابت بطبيعته (`timestamptz`, لا `updated_at`) |

**لا حقل `updated_at`**: السجلّ بمجرد إدراجه لا يُعدَّل أبداً (انظر §4 عن RLS).

## 3) لحظة الالتقاط (متى يُنشأ سجلّ ثابت؟)

الزناد الأساسي المقترح: **تأكيد الدفع من جانب الخادم (Webhook)**، لا تصدير الملف.

**السبب**: تأكيد الدفع يحدث بالفعل في سياق موثوق تماماً — دوال `webhook-moyasar`/`webhook-stripe`/
`webhook-tamara` (`supabase/functions/webhook-*/index.ts`) تتحقق من توقيع/سرّ المزوّد أولاً
(`verifyMoyasarSecretToken`/`verifyStripeSignature`/إلخ)، ثم تتحقق من تطابق المبلغ فعلياً
(`verifyOrderAmount`)، ثم تُحدِّث `orders.status = 'paid'` **مرة واحدة فقط** بفضل القيد الفريد
`orders_provider_ref_unique` (منع معالجة نفس حدث الدفع مرتين). هذه هي اللحظة الوحيدة في كامل
النظام التي تُثبِت فعلياً "العميل دفع مقابل هذه الدراسة الآن" بلا إمكانية تلاعب من طرف العميل —
تماماً نفس ضمان الثقة الذي بُني عليه جدول `orders` نفسه (2026-07-09: "لا يوجد أي مسار يسمح للعميل
بكتابة/تعديل حالة 'مدفوع' بنفسه").

مقابل ذلك، **تصدير الملف (PDF/Word) زناد أضعف**: يحدث بالكامل في المتصفح (`ReportGenerator.js`)،
لا يمرّ بأي تحقق خادمي، ولا يوجد ما يمنع تصديرين لنفس الدراسة بمدخلات مختلفة قليلاً بفارق ثوانٍ.
لذلك **لا يجب** أن يكون تصدير الملف زناد تجميد رسمي — لكن من المعقول إتاحته كزناد ثانوي اختياري
("جمّد هذه النسخة يدوياً") لعميل لم يدفع بعد أو يريد نسخة مرجعية أثناء العمل، مع تصنيف واضح
(`capture_trigger = 'manual_export'` أو `'owner_request'`) يميّزه بصرياً ووظيفياً عن السجلّ
المرتبط بدفع فعلي (`payment`) — الأخير هو "الرقم الرسمي"، البقية مرجعية فقط.

**التنفيذ المقترح لاحقاً (خارج نطاق هذه الوثيقة)**: داخل كل دالة webhook، بعد نجاح تحديث
`orders.status = 'paid'` مباشرة، حساب `calculateStudy` على `study.data` الحالية (الدالة تعرف
`study_id` من الطلب) وإدراج السجلّ الثابت في نفس المعاملة منطقياً (أو عملية تالية فورية تُعيد
المحاولة عند الفشل — فشل التجميد لا يجوز أن يُسقِط تأكيد الدفع نفسه).

## 4) مكان التخزين: توسيع `study_versions` القائم، لا جدول جديد

جدول `study_versions` (`supabase/migrations/20260721180000_study_versions.sql`) موجود حياً
منذ 2026-07-21 لكنه **غير مستخدَم إطلاقاً في أي واجهة اليوم** (موثَّق في تعليق الترحيل نفسه). شكله
الحالي قريب جداً مما تحتاجه هذه الميزة:

```sql
create table public.study_versions (
  id uuid primary key default gen_random_uuid(),
  study_id uuid not null references public.studies(id) on delete cascade,
  version_number integer not null,
  data jsonb not null,           -- المدخلات فقط اليوم
  change_summary text,
  created_by uuid references auth.users(id),
  created_at timestamptz default now()
);
```

**التوصية: توسيع هذا الجدول بدل جدول جديد منفصل**، لتفادي تكرار نفس مفهوم "لقطة دراسة عبر
الزمن" في مكانين. الأعمدة الإضافية المطلوبة:

```sql
alter table public.study_versions
  add column if not exists outputs jsonb,
  add column if not exists engine_version text,
  add column if not exists schema_version text,
  add column if not exists capture_trigger text
    check (capture_trigger in ('payment', 'manual_export', 'owner_request')),
  add column if not exists order_id uuid references public.orders(id),
  add column if not exists is_frozen boolean not null default false;
```

`is_frozen = true` حصراً للسجلّات ذات `capture_trigger = 'payment'` — يميّز "الرقم الرسمي" عن أي
لقطة مرجعية أخرى (بما فيها أي استخدام مستقبلي محتمل لهذا الجدول لغرضه الأصلي: استعادة نسخة
عمل سابقة أثناء التحرير، غير مرتبطة بدفع إطلاقاً).

### تعارض حرج في سياسة RLS القائمة — يجب إصلاحه قبل أي استخدام لهذه الميزة

سياسة `study_versions` الحالية:

```sql
create policy "Users can manage versions of own studies" on public.study_versions
  for all using ( ... user_id = auth.uid() ... );
```

`for all` تمنح صاحب الدراسة **حذف وتعديل** سجلّات نسخه الخاصة، لا قراءة/إدراج فقط. هذا يتناقض
جوهرياً مع معنى "تجميد": لو استطاع العميل حذف أو تعديل السجلّ الرسمي المرتبط بدفعه، فلا قيمة
لكونه "ثابتاً" أصلاً — تماماً نفس درس RLS المتكرر هذا الأسبوع (تقييد الصفوف لا الأعمدة). **قبل
تفعيل هذه الميزة فعلياً**، يجب تضييق السياسة لسجلّات `is_frozen = true` تحديداً إلى `select`
و`insert` فقط (لا `update`/`delete` حتى لصاحب الدراسة نفسه)، مع إبقاء `for all` كما هي فقط
للسجلّات غير المجمَّدة (`is_frozen = false`) إن استُخدم الجدول لاحقاً لغرضه الأصلي (استعادة نسخة
عمل). عملياً هذا يعني سياستين منفصلتين بدل سياسة `for all` واحدة، تُفرَّق بشرط `is_frozen`.

`insert` نفسها يجب أن تكون عبر **Edge Function بمفتاح service_role فقط** لسجلّات `payment`
(بنفس نمط `orders` — "لا يوجد أي مسار يسمح للعميل بكتابة الحالة بنفسه") لا مباشرة من العميل، وإلا
استطاع أي مستخدم إدراج سجلّ "مجمَّد" مزوَّر يدّعي أنه رسمي.

## 5) سلوك إعادة الفتح بعد تغيّر المحرك

عندما يفتح المستخدم دراسة لها سجلّ ثابت (`is_frozen = true`) والمحرك الحالي مختلف عمّا
سُجِّل فيه:

- **العرض الحيّ يبقى حياً** (`ProjectOverviewView`/`DecisionDashboard`/التصدير) — لا رجوع عن قرار
  المرحلة 2 بأن التصدير يعيد الحساب دائماً؛ هذا يبقى الافتراضي الصحيح لأي دراسة لم يتجمَّد لها شيء
  بعد، وحتى للدراسات المجمَّدة يفيد العميل رؤية "لو أعدت الحساب اليوم، هذا ما تحصل عليه".
- **بجانب العرض الحيّ**، رابط/بطاقة صريحة "الرقم الرسمي وقت الدفع" تفتح السجلّ المجمَّد كما هو
  (بلا أي إعادة حساب) — هذا هو الاستخدام العملي لبانر إصدار المحرك من المرحلة 2: بدل تنبيه عام
  "الأرقام قد تختلف"، يصبح بإمكانه أن يربط مباشرة لمقارنة صريحة "الحيّ الآن" مقابل "المجمَّد وقت
  الدفع"، بنفس أرقام NPV/IRR/القرار جنباً إلى جنب.
- **لا محاولة "ترحيل" (migrate) السجلّ المجمَّد للمحرك الجديد تلقائياً** — أي إعادة حساب على
  `inputs` المخزَّنة بالمحرك الحالي تنتج NPV مختلفاً بالتعريف (هذا بالضبط سبب وجود `ENGINE_VERSION`
  أصلاً)؛ لو احتاج العميل رقماً رسمياً محدَّثاً، الحل الصحيح هو تجميد جديد (دفعة/طلب جديد)، لا تعديل
  القديم — يحافظ على معنى "ثابت" بلا استثناء.

## 6) الأثر على `study_versions` كآلية عامة

توسيع الجدول (§4) لا يكسر أي استخدام قائم لأنه **لا يوجد استخدام قائم** (مؤكَّد: صفر مراجع من
`web/` حتى تاريخ هذه الوثيقة). الأعمدة الجديدة كلها اختيارية (`nullable`، بلا `not null` جديد)
فلا حاجة لأي backfill. لو استُخدم الجدول لاحقاً لغرضه الأصلي (نسخ عمل عادية أثناء التحرير، غير
مرتبطة بدفع)، تلك السجلّات ببساطة تترك `outputs`/`engine_version`/`order_id`/`capture_trigger`
فارغة و`is_frozen = false` — لا تعارض بنيوي بين الاستخدامين.

**آلية `_versionHistory` في `store.js` (سجلّ محلي في المتصفح، آخر 10 نسخ، `IndexedDB`/`localStorage`
عبر `storageManager`) منفصلة تماماً ولا علاقة لها بهذه الوثيقة** — تلك للاسترجاع الفوري من خطأ
تحرير عرضي (نطاقها الجهاز نفسه، لا تُزامَن للسحابة، لا سياسة RLS لها لأنها ليست في قاعدة البيانات
أصلاً). لا تعديل مطلوب عليها.

## 7) خارج النطاق صراحة في هذه الوثيقة

- أي كود تنفيذي (SQL فعلي، Edge Function، تعديل واجهة) — هذه وثيقة تصميم فقط.
- واجهة "قارن النسختين" التفصيلية (جنباً إلى جنب) — قرار تصميم واجهة منفصل عند التنفيذ.
- تسعير/شروط تجارية لعرض "الرقم الرسمي" (هل يظهر لكل العملاء أم فقط الباقات المدفوعة بالكامل؟) —
  قرار مالك عند التنفيذ.
- التنفيذ الفعلي نفسه — مؤجَّل حتى أول عميل دافع حقيقي حسب قرار المالك 2026-08-28.
